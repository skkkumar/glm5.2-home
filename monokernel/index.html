01

Memory bound, compute bound, latency bound

Every GPU kernel does two things: it moves data between HBM and the cores, and it does math on that data. Whichever takes longer is the bottleneck.

  • Memory bound: the cores wait for data. Element-wise ops, and LLM decode, where each weight is read once per token and used for very little math.
  • Compute bound: the data arrives fast enough and the cores are busy the whole time. Big matrix multiplies, LLM prefill.
  • Latency bound: neither. The kernel is too small to keep either the memory pipe or the cores busy, and fixed costs (launch, drain, sync) set the time.
The roofline only tells you the ceiling. A point far below both roofs is latency bound. The MonoKernel doesn't move the point sideways (the math is the same); it pushes it up.

Why decode at 2–8 tokens lands in the gap

For each layer the GPU reads the layer's weights once and does about 2 FLOPs per weight per token. At 8 tokens with FP8 weights that is roughly 16 FLOPs per byte, against a ridge near 300. Decode is deeply memory bound on paper. But the old kernel chain never reaches the memory roof either: each of its nineteen kernels moves only a few MB, pays a launch, drains to HBM, and waits for its slowest block. Bandwidth is only "available" if enough bytes are in flight (Little's law: at 8 TB/s and ~1 µs latency you need ~8 MB outstanding at all times), and a kernel that moves 2 MB in total can never get there.

The extended roofline: what fusion actually recovers

Add a fixed cost to the model: time = T₀ + max(bytes ÷ BW, FLOPs ÷ peak). Now the ceiling depends on how big the kernel is.

MI355X-like numbers: 8 TB/s, 2.5 PFLOP/s bf16, T₀ = 5 µs. A 1 MB kernel sits ~25× under the roof at every intensity. A 256 MB kernel nearly touches it. The old chain was on the red curve, nineteen times per layer. The MonoKernel pays T₀ once and moves the whole layer's weights in that launch, sliding to the green curve. Same x position; different curve.

You need four words to read this kernel. Two are hardware, two are software.

What an ALU is, and the three kinds here

An ALU (arithmetic logic unit) is the circuit that does the math: numbers in from registers, one operation, result back. Everything else exists to feed it. A CDNA CU has three kinds: the vector ALU on each SIMD, 64 lanes wide, for per-element work (softmax exponentials, scale multiplies, RMSNorm, the top-k histogram, tag compares); the matrix core, a specialised ALU that does a whole small matrix multiply per instruction, which is where all the projections and expert math go; and the scalar ALU, one per CU, for values that are the same across a wave (addresses, loop counters, branch decisions). "Compute bound" means the matrix cores are the bottleneck; "memory bound" means they're waiting for data; "latency bound" means they're waiting for something else, like a launch or a sync.

A wave is a running program, not a store of instructions

The kernel code lives once, in memory, behind an instruction cache. Every wave runs that same code. What makes waves different is where they are in it and what data they hold: a program counter, 64 lanes of registers, an execution mask for divergent branches, and the counters s_waitcnt checks. A wave slot on a SIMD is a place to keep that state live. The analogy: the recipe is printed once on the wall; each wave is a cook at their own station, partway through it, with their own ingredients; the SIMD is one burner, and each cycle one cook gets to use it. Parking a cook costs a station (registers), not a copy of the recipe. All 131,072 threads run the same kernel.py; each wave decides what to do from its own bid, wave and lane.

Waves and clock cycles

There is one clock for the CU. Each SIMD issues at most one instruction per cycle, from one ready wave. In the classic GCN/CDNA scheme the CU's scheduler visits the four SIMDs in rotation, so each SIMD gets a turn every 4 cycles, and a wave64 vector instruction occupies the ALU for 4 cycles, which lines up. On a turn the SIMD can issue to several different units at once (vector, scalar, memory, LDS, branch) as long as they come from different waves. For performance reasoning the simple version is enough: per SIMD, one vector instruction in flight at a time, so a wave with nothing independent to do stalls, and either another wave or more ILP fills the gap. What matters is latency (an HBM load is hundreds of cycles; an MFMA tens, more for bigger shapes) against issue rate. The MonoKernel has only two waves per SIMD to switch between, so it fills the gaps with ILP: weight loads issued before the mailbox wait, several MFMA chains per wave.

Resident is not executing

Each SIMD holds up to 8 parked waves, so a CU can hold 32, but per cycle each SIMD issues one instruction from one ready wave. The others wait. Parking waves is a latency-hiding tool: while one wave waits hundreds of cycles for HBM, another can run. The MonoKernel uses only 8 of 32 slots (25% occupancy) and hides latency with ILP instead: each wave issues all its weight loads before it waits for its inputs, and keeps several MFMA chains going. The empty slots are deliberate: the kernel's LDS and register footprint keep any other workgroup off the CU, which is what guarantees all 256 CTAs are resident at once.

The counting, once: 2 waves × 4 SIMDs = 8 waves = 512 threads = 1 CTA per CU. 256 CUs → 256 CTAs → 131,072 threads, 2,048 waves, all live for the whole layer.

Occupancy math, and why the MonoKernel runs at 25% on purpose

This section follows AMD's Occupancy Math on the MI355X guide (Pandey, Li, Luo; ROCm blog, July 2026), keeping only what you need to read this kernel. Its one-line thesis: occupancy is a diagnostic, not a goal, and matrix-bound kernels hit peak at a fraction of full occupancy.

The budget, per CU

ResourceBudgetPrivate toNote
VGPRs512 per laneeach SIMDregular (≤256) + accumulator (≤256) draw on one file; CDNA3 unified them, CDNA4 keeps it. Allocated in groups of 8.
SGPRs~800 per SIMD, ≤102 per waveeach SIMDwave-uniform values; rarely binds
LDS160 KBthe CU2.5× CDNA3's 64 KB; shared by all four SIMDs
Wave slots8 per SIMD, 32 per CUeach SIMDplus a limited pool of hardware barriers per CU

The hinge of the whole calculation: registers are per-SIMD, LDS is per-CU. A wave on SIMD 0 can't touch SIMD 1's registers, but every wave in a workgroup sees the same LDS.

The four limiters

VGPR limit:  floor( 512 / total-VGPRs-per-lane )   → waves / SIMD   (regular + accumulator)
SGPR limit:  floor( ~800 / SGPRs-per-wave )        → waves / SIMD
LDS  limit:  floor( 160 KB / LDS-per-workgroup )   → workgroups / CU
WG   limit:  max resident workgroups per CU         (slots + barriers)

occupancy = min(all four, converted to waves/SIMD), clamped at 8/SIMD, 32/CU

The unit trap: VGPR and SGPR limits are waves per SIMD, the LDS limit is workgroups per CU. Convert before taking the minimum. A 4-wave workgroup puts one wave on each SIMD, so n workgroups per CU = n waves per SIMD. An 8-wave workgroup puts two on each SIMD, so each workgroup costs two waves per SIMD. That second case is this kernel.

Why the ceiling is rarely the target

Occupancy hides latency by switching between parked waves (TLP). Little's Law says what you actually need is independent operations in flight = latency × throughput. For the matrix core, if an MFMA takes L cycles to retire and the unit accepts one every T cycles, you need about L/T independent MFMAs in flight. You can get them from many waves of one chain each (TLP), or from one wave running several independent accumulator chains (ILP). Both satisfy the law; both spend the same 512-VGPR file.

The blog measured this directly: a single scaled MFMA in a loop with K independent accumulator chains, occupancy throttled separately. With 8 chains per wave the matrix core held about 97% of its ~5 PFLOP/s peak from one wave per SIMD (12% occupancy) upward; with one dependent chain it starved at the same floor. Same chip, same register file, two ways to spend it; the low-occupancy, high-ILP route wins. (The benchmark keeps operands in registers and moves no memory, so real kernels land lower.)

The memory side follows the same law: bytes in flight = HBM latency × bandwidth. At 8 TB/s and sub-microsecond latency that's a few MB across the GPU, tens of KB per CU. A handful of waves each issuing wide buffer_loads with several outstanding before the s_waitcnt saturates the bus. The lever is bytes-per-wave in flight, not wave count.

The trap, and the roofline underneath

More waves per SIMD means fewer VGPRs per wave, so a smaller accumulator tile, so lower arithmetic intensity, so more traffic per MFMA, so the matrix core waits. Arithmetic intensity is set by tile size, not occupancy. For MFMA-bound kernels the sweet spot is routinely 2–4 waves per SIMD, not 8. The MI355X machine balance is about 5 PFLOP/s ÷ 8 TB/s ≈ 625 FLOP/byte for MXFP8; with the bf16 MFMA this kernel uses, roughly half that. Decode at 2–8 rows sits two orders of magnitude below either ridge.

Applied to the MonoKernel

  • Occupancy by construction: 8 of 32 waves per CU, 25%. One 512-thread workgroup, two waves per SIMD. In the blog's terms, the workgroup limit is pinned at 1 per CU; the kernel's LDS use (xs up to 96–144 KB, WORK_WORDS ≤ 32768 words) and register footprint are what enforce it. That is the point: the design needs every CTA resident, and a second workgroup landing on a CU would break the "one CTA per CU" assumption the mailbox waits rely on.
  • It's the ILP route. With only two waves per SIMD to switch between, TLP can't hide much. So each wave keeps its own latency covered: u_qb issues both units' 1 KB loads before hint_wait, run_units prefetches the next batch before computing the current one, and each wave advances its accumulator across 4 sub-passes per unit. That's the blog's "wide loads, several outstanding, before the waitcnt" recipe.
  • It's memory-bound, so the matrix-core argument matters less than the HBM one. The figure of merit is achieved bandwidth during decode. The blog's Little's-Law number, tens of KB in flight per CU, is exactly what the 8 waves × 2 units × 1 KB = 16 KB of outstanding weight loads per task provides.
  • LDS is spent the way the blog recommends. Accumulators stay in registers; LDS holds the staged input (xs) and the cross-wave reduction (red), i.e. pipeline depth and cooperation, never the hot accumulator.
  • Measure the right thing. By the blog's workflow, step 3 ("is occupancy even your problem?") answers itself here. Pull MfmaUtil, VALUBusy and achieved bandwidth from rocprofv3, and the kernel's own timeline=True stamps for per-stage wait vs. compute.

How one decode step becomes one launch per layer

Before, every operation was its own kernel. The kernel ending was the barrier; HBM was the hand-off. The MonoKernel keeps one grid resident for the whole layer and uses each memory tier for what it's good at.

TierBefore (kernel chain)MonoKernel
Registers, LDS (per CU)Die with each kernelTask tiles, MFMA accumulators, the top-k histogram
L2 (shared)Cold at every kernel startThe mailboxes: small (value, tag) pairs, written just before they're read
HBMEvery intermediate + weights + cacheWeights, KV / index cache, and only the two big scratch regions
Peer GPUsSeparate RCCL all-reduce kernelIPC writes into peer buffers from inside the kernel

One correction to the slogan: it's one launch per layer, not per step. A step is still ~78 stream-ordered launches, captured into a CUDA graph, plus one advance_step() per runtime. What collapsed is each layer: nineteen kernels to one.

One kernel, two homes, now in-tree

The kernel was first upstreamed in two halves: the FlyDSL source in AITER (#6173) and a ~530-line caller in vLLM (#60216). Both are now closed in favour of #60831, which carries the whole package inside vLLM. It has eight commits: the port itself; per-layer routing, staged refusals and cache checks (kernel source moves to amd/ops/mono, integration to amd/mono/); bounded polls and fail-stop; dropping every variant vLLM doesn't use; tests and CI (tests/models/deepseek_v32/amd_mono/: dense, MoE, paged indexer, routing, safety, weights); dropping the unpacked attention weights; checking only real rows; and cleanup. The kernel still needs FlyDSL installed to compile.

The call chain in vLLM

How the hook works: the model calls GlmMono.forward_layer for every decoder layer. At the first layer, _begin_step() asks spec.step_reason() whether this forward is a kernel step: 1, 2, 4 or 8 tokens, a pure decode step (max_query_len == 1), and not a piecewise CUDA graph. That decision depends only on what every TP rank builds alike from the scheduler output, because each launch all-reduces inside the kernel; a split decision would hang. If it is a kernel step, every layer is one launch, and each returns a zero partial sum plus the full residual stream, so vLLM's own layer code adds nothing. Otherwise all layers run the normal path.

Refusals are staged and loud. spec.refuse_config() runs before weights load and lists every reason at once: gfx950 with 256 CUs, glm_moe_dsa, TP 4 or 8, no PP/DP/EP/EPLB/DCP, no speculative decoding, LoRA, KV transfer or sleep mode, an fp8 KV cache, indexer_rope_interleave, Model Runner V2, and FULL (not piecewise-only) CUDA graphs. _refuse_model() checks the loaded weights per layer. A one-token step is padded to 2 rows (spec.width_for): the pad row gets slot −1 and attends to nothing. Dense layers are faked as MoE with expert-sized MXFP4 slices and no router. The log line states the numerics up front: expert inputs quantised to MXFP8 where vLLM uses MXFP4, and the TP all-reduces done in bf16 inside the launch.

Inside one launch: the stages

These are the real stage names from glm/layout.py → stage_tasks(). Seven of them are the same GEMV skeleton with different weights; two call MFMA directly on gathered cache data; three have no MFMA at all.

Three ideas make it work

  1. One persistent grid, no grid barrier. 256 CTAs × 512 threads. Each stage is a list of tasks; task t runs on CTA (base + t) mod 256. All CTAs are resident and dependencies only point backwards, so a CTA can spin-wait for its inputs without deadlocking.
  2. Tagged mailboxes instead of flags. A value and this launch's epoch tag are stored together in one write. The reader polls until the tag matches. One round trip per hand-off, no clearing between layers. (Section 08.)
  3. GEMVs on matrix cores. Weights are pre-packed so one wave loads a contiguous 1 KB tile; FP8 is widened to bf16 and fed to mfma_f32_16x16x32_bf16 with the 2–8 tokens as the N dimension. Weight loads that don't depend on earlier stages are issued before the CTA waits for its inputs.

Global memory: scratch, peer buffer, mailboxes

The kernel touches three kinds of global memory. The scratch buffer is private to each GPU and holds the mailboxes between stages. The symmetric peer buffer is exported with HIP IPC so every GPU can write into every other GPU's copy; that's the in-kernel all-reduce. And vLLM-owned buffers come in as pointers: the input h, output x_out, packed weights, KV and index caches, cos/sin, the step counter, and out_indices.

Sizes below come from running the PR's own layout() (ops/mono/glm/layout.py) with the GLM-5 config. Change the settings and watch which regions dominate.

What stands out

  • Two regions dominate: sp_acc and index_scores. sp_acc holds the split-softmax partials, one 512-wide accumulator per split, head and row. index_scores is one score per past token per row, so it grows with max_model_len.
  • Every value is stored as a (value, tag) pair: 8 bytes for a 4-byte value. The mailbox design roughly doubles scratch size. That's the price of a one-round-trip hand-off.
  • One scratch is reused by all layers in a step, which the epoch tag makes safe. But there is one runtime per width (2 / 4 / 8) × indexer / non-indexer, so up to six scratch and six peer buffers per GPU. The current layout adds three tiny regions the widget doesn't show, poll_abort, poll_err_addr and poll_xrank_addr, for the bounded-poll fail-stop, and the peer buffer gains a poll_xrank word per rank (plus a dcp region that is empty at DCP 1).

What a mailbox is

Physically, a mailbox is a slice of the scratch buffer: one torch.zeros(nbytes, uint8) made once when the runtimes are built. mb("q_an") is just scratch + offset, with the offset baked in at compile time. In practice the hot ones live in L2.

A better picture than "dictionary" is a pigeonhole wall: a fixed grid of numbered 8-byte boxes, every box with a date stamp. The sender puts a value in box 37 stamped with today's date. The receiver checks box 37 and reads it only if the date is today. The names are labels painted on sections of the wall for humans.

  • Writer (put): one buffer_store of the pair [value, tag] as a single 8-byte write, so a reader never sees a new tag with an old value.
  • Reader (poll): load the pair, compare the tag to its own epoch. Match → fresh, continue. Else s_sleep briefly and reload. Loads use the sc1 cache modifier so they bypass this CU's stale L1; peer-buffer loads use sc0 sc1 to be visible across GPUs.

Why the tag is step × launches_per_step + layer + 1

  • × launches_per_step: layer l of step s gets a tag in [s·L+1, s·L+L], so no two launches in the server's life share a tag and the sequence is strictly increasing. Anything left by the previous layer or the previous step fails the compare. That's what lets every layer share one scratch buffer.
  • + 1: scratch starts as zeros, so tag 0 must mean "never written". Without the +1, step 0 layer 0 would read garbage as "ready".
  • Why split step and layer: layer is a kernel argument baked into the CUDA graph; step is read from a device-memory counter that advance_step() bumps once per step. So the captured graph never changes, and the only thing that moves between replays is one integer in memory.

The tag is 32-bit, so it wraps after about 2³² ÷ L steps (≈55 million at 78 layers). Theoretically possible, not handled, and a fair reviewer question.

Bounded polls and fail-stop

A spin-wait that can never end is a hung GPU, so #60831 bounds every mailbox wait: a poll gives up after spec.POLL_LIMIT (20 million) retries, or sooner if a peer has raised the shared abort mark. An expired wait writes a sticky word per stage into the scratch (poll_abort, poll_err_addr) and, for cross-rank waits, into rank 0's peer buffer (poll_xrank). _HealthWatch copies those words to pinned host memory every step and checks the previous copy once its event completes, one step late and never blocking. On a hit, _fail_stop terminates the worker (non-output ranks exit immediately; rank 0 raises and exits after a grace period) so no rank is left spinning in a collective. The test-only VLLM_MONO_UNSAFE_WARN=1 downgrades that to a warning.

Worked example: the q_b stage

q_b is the second half of MLA's query path. GLM-5 doesn't produce the query with one big projection; it goes 6144 → 2048 (q_a), RMSNorm, then 2048 → 16 heads × 256 (q_b). The bottleneck saves parameters: 12.6M + 33.5M instead of ~100M per layer.

It is a matrix multiplication

Q = q_an · W_q_bᵀ, q_an is S × 2048, W_q_b is 4096 × 2048, Q is S × 4096. With S = 2–8 it's a very skinny one, which people call a GEMV. Per sample the math is 2 × 2048 × 4096 ≈ 17 MFLOP; the weight read is 8 MB regardless of S. At S = 2 that's about 4 FLOPs per byte: memory bound by a mile.

The 4096 rows are rows of the weight matrix, and each weight row produces one output feature. 4096 ÷ 16 rows per task = 256 tasks, one per CTA at TP4. Each head is 256 rows, so tasks 0–15 are head 0, 16–31 head 1, and within a head the first 12 tasks write q_nope, the last 4 write q_pe after RoPE.

Inside one task

Only x is staged into LDS. Weights go HBM → registers → MFMA, each 1 KB tile read by exactly one wave, exactly once. The activations are tiny but every wave needs all of them, so they're copied once into xs and read eight times. That's why the LDS footprint scales with S × K, never with weight size.

The MFMA

So: one wave computes all 16 rows for all S sample columns, but only for its eighth of K. Eight partial 16 × 16 tiles, summed through LDS, make the answer. K is split rather than rows because 16 is the MFMA's minimum height; splitting K keeps every MFMA full-sized while dividing the 2048-wide weight read eight ways.

Per q_b task at TP4: 8 waves × 2 units × 4 MFMAs = 64 MFMA instructions, each reading 1 KB of weights that u_qb had already requested before the mailbox wait.

Besides MFMA, what instructions run

  • VMEM: buffer_load of weight tiles (the dominant traffic); scales and RoPE tables; mailbox put / poll; KV and index cache reads and writes; IPC stores into peer GPUs.
  • LDS: lds_ld / lds_st on xs, red, outs and the top-k histogram.
  • VALU: fp8/mxfp4 → bf16 widening, block-scale multiplies, RMSNorm (rsq), RoPE, softmax exp/max/sum, SiLU, residual adds, activation quant, radix counting.
  • Cross-lane: xshfl, bpermute, readlane, DPP reductions for wave-wide max and sum without LDS.
  • SALU: the address arithmetic that is the same across a wave (start, mb offsets, loop counters).
  • Sync: ~93 gpu.barrier(), compiler-inserted s_waitcnt, s_sleep in poll loops, s_memrealtime for the timeline.

Weights dominate, and w_o is the single biggest read at 24 MB because it projects back to the full 6144 width before the all-reduce. The full expert tables are ~860 MB and ~430 MB per GPU, but only the routed experts are read, which is why batch helps MoE. The index-cache scan is the biggest activation-side read and the only one that grows with context. Everything always-read sums to roughly 55 MB per layer plus routed experts plus cache reads: on 8 TB/s that is a floor near 20 µs per layer, which is what the MonoKernel is trying to approach.

The kernel's abstractions, and where they live

Read it top-down and it's layer → stage → task → tile. Read it bottom-up and it's lane → wave → CTA. The task is where the two meet: one CTA, one task, eight waves sharing it.

Warp specialisation, one level up

Warp specialisation gives different warps in a CTA different roles (loader, MMA, storer) and hands tiles through LDS. The MonoKernel does the same trick with whole CTAs as the units and stages as the roles, handing data through global mailboxes. Inside each CTA the eight waves are mostly homogeneous (same job, different K-slice), with two exceptions: wave 0 does the multi-producer polling, and every wave software-pipelines itself by issuing weight loads before it waits. On CDNA, which has no TMA or mbarrier, that per-wave prefetch is most of what a loader warp would buy. Combining both is a possible follow-up for the weight-streaming stages, not something the PR claims.

The FlyDSL API it's written in

FlyDSL is a Python-embedded DSL: you write the kernel as Python, FlyDSL traces it into MLIR (gpu, rocdl, llvm dialects), and LLVM compiles that to GFX950 code. The mental model: Python runs once at build time and emits the GPU program. By run time the MLIR is gone; launch() just hands a compiled code object to HIP with 44 pointers and ints.

Limits, lineage, and what comes next

Is it a hard-coded megakernel?

Mostly yes. GLM-5's shapes are module-level constants (HIDDEN, KV_LORA, N_EXPERTS, …), BLOCKS = 256 matches the MI355X CU count and the persistent design needs every CTA resident, and the deployment is fixed to TP4/8, chunks of 2/4/8 rows, top-k 2048, fp8 KV, block-FP8 attention weights and MXFP4 experts. What's flexible is that it's a generator: FlyDSL compiles a specialised kernel per combination of samples, TP, indexer, cache layout and dense slices. It is a hand-tuned kernel for one model on one GPU, like the TileRT MonoKernel it references, not a general megakernel compiler like Mirage's MPK.

Why not 32 rows?

The kernel asserts S ≤ 12. The MFMA tile is 16 columns wide, so S = 16 is the natural ceiling of one accumulator. The real cap is LDS: qkv_a stages S × 6144 bf16 into xs, 96 KB at 8 rows, 144 KB at 12, 192 KB at 16, against 160 KB. Per-row scratch and task counts grow too (split is S × heads × 32 tasks). And the payoff shrinks: at 32 rows a batched GEMM is already near the memory roof, so the latency gap the kernel closes is smaller just as the engineering cost rises. Today spec.step_reason() accepts only 1, 2, 4 or 8 tokens; a 32-token step falls back to the normal chain.

Why 16 is the next step, and it's small

At 16 every MFMA column carries a real row; the padding disappears. The only thing over budget is qkv_a's staging, and each wave only ever reads its own K-slice of xs, so staging x in two K-halves (or reading the B operand straight from the mailbox into registers, as the weights already do) removes the limit without touching the stage order, bases or mailbox contract. Then add 16 to spec.STEP_TOKENS and the kernel's SUPPORTED_SAMPLES, a fourth compiled width in _build(), and regenerate layout(). At 16 rows the intensity is ~32 FLOP/B against a ridge near 300, so the fusion win is nearly as large as at 8.

A group of megakernels for bigger batches

Splitting at the all-reduce after o_proj into an attention kernel and an MoE kernel is the sane middle ground above 16: each phase gets its own tiling (per row and head for attention; per expert with rows sorted by expert for MoE), the LDS budget resets, and the cost is one launch gap per layer instead of eighteen. The MoE half is close to what AITER's fused MoE already is; the sparse-attention chain (indexer, top-k, gather, split, merge) is where a persistent kernel keeps paying at mid-batch. The mailbox contract can survive the seam: the attention kernel's o stage writes a as tagged pairs, the MoE kernel's router polls them.

Where the mailbox idea comes from

The kernel's docstring says it: the tagged-pair protocol ("payload + launch epoch is the progress protocol for resident CTAs") is from TileRT's MonoKernel, the tile-ai / TileLang team's persistent decode runtime for DeepSeek-V3.2 and GLM-5 on NVIDIA, which also plugs into vLLM as a decode engine through the V1 KVConnector. The port came through ROCm/ATOM#2435 into AITER and FlyDSL, and now lives in vLLM's tree. Underneath TileRT, the packed data+flag word is the shape of NCCL's LL protocol, and the resident-CTAs-walking-a-stage-list pattern is the 2025 megakernel line (Hazy Research's counters, Mirage MPK's event table). TileRT's contribution was the monotonically increasing launch epoch as the flag, which is what makes CUDA-graph replay clean with no reset kernel. The ISA-level realisation here (buffer stores with sc1, DPP polling across 64 lanes, IPC peer slots) is the AMD side's.
