The PRs, in model order

MLA attention

1

Don't re-quantize bf16 MLA kv_b_proj to fp4/fp8 for GLM MoE DSA

Where: MLA, the kv latent projection that expands the compressed note back into keys and values. Weight-loading step.
vLLM #48051amd-sriramDraftquantizationglmopened 8 Jul

The ROCm AITER MLA path assumed any bf16 kv_b_proj weight was unquantized and squeezed it to fp4/fp8. In amd/GLM-5.2-MXFP4 the MLA weights are meant to stay bf16; only the experts are MXFP4.

fp4 re-quantization added about 11% error per attention layer; it stacked up across 78 layers and pushed greedy decoding into repetition loops. After the fix, "What is the capital of France?" ends with "Paris".
PR #48051
2

Fuse decode QK-RoPE + Q-concat + KV-concat + KV-cache write for sparse MLA

Where: the attention block itself, the per-layer query and key preparation that runs right before MLA attention reads the 2,048 notes.
vLLM #47757xaguilar-amdOpen7 commitsopened 6 Jul

On ROCm the sparse-MLA decode path ran four back-to-back ops per layer: RoPE on the position parts of q and k, the query concat, the KV concat, and the fp8 KV-cache write. This collapses them into one AITER kernel, fused_qk_rope_concat_and_cache_mla, dispatched from the MLA layer with a clean fallback whenever the gate does not apply (non-ROCm, no AITER, non-fp8 cache). Positions travel as a real argument because a forward-context stash was not torch.compile or CUDA-graph safe.

GLM-5.2-FP8 on gfx942, TP=8: TPOT and throughput about 1.02 to 1.04× across the sweep (for example +3.7% at ISL 1024 concurrency 1, +4.0% throughput at ISL 8192 concurrency 32). gsm8k 0.94, unchanged. The MTP drafters reuse the same MLA layers, so they get the fusion too.
PR #47757

Indexer — vLLM side (what gets called, and when)

3

Optimize rocm aiter sparse mla indexer

Where: indexer prologue and top-k. The PR that first wired three AITER kernels into the sparse path: cp_gather_indexer_k_quant_cache, indexer_k_quant_and_cache, top_k_per_row_decode.
vLLM #46172tjtanaa (EmbeddedLLM)Openopened 19 Jun

Follows the "speed of light" layout from AMD's ATOM plugin for top-k 2,048, so vLLM and ATOM share the same AITER kernels going forward. It also introduced the module-level FP8_DTYPE constant that pin 10 finishes wiring up.

Validated on DeepSeek-V3.2 at 1M context: gsm8k about 0.95 at block sizes 1 and 64, with performance gains from all three kernels. This is the foundation most of the amber indexer pins build on.
PR #46172
4

Enable fused indexer-Q RoPE+quant kernel for DeepSeek/GLM sparse attention

Where: indexer stage 1, the query side of the prologue. Pin 5 is the matching key side.
vLLM #47335xaguilar-amdOpen3 commitsopened 1 Jul

The fused_indexer_q_rope_quant kernel already existed in vLLM and already ran on CUDA; on ROCm the same work fell back to a chain of small Triton and elementwise kernels per sparse layer per decode token. A two-line enablement turns it on for glm_moe_dsa: query-side RoPE, FP8 quantization and the weight-scale fold become one launch, four Q-side kernels → one.

About 170 ms of self-GPU time reclaimed on rank 0 over a decode capture, roughly 0.7% of the total; a consistent 0.3–0.9% end-to-end improvement on GLM-5.2-FP8 at TP=8 with no credible regression. gsm8k 0.9469, unchanged.
PR #47335
5

Fuse the DSA indexer prologue with AITER

Where: indexer stage 1, the key side of the prologue. Four kernels, K normalization, Q/K RoPE, FP8 quantization, K-cache write, become one fused AITER kernel.
vLLM #51315amd-sriramOpenneeds-rebaseopened 6 Aug

Uses AITER's fused indexer_qk_rope_quant_and_cache kernel for the supported BF16/FP8 shape; other shapes keep the old path.

Launches 4 → 1. Decode stage 17.4 µs → 5.9 µs (−66%), prefill 164 µs → 271 µs (+65%). Net prologue GPU time −4.8%; throughput +0.7%, TPOT −0.7%. Accuracy unchanged.
PR #51315
6

Skip cleaning sparse prefill MQA logits

Where: indexer stage 2, prefill path. The buffer holding the scores of the new word against every note.
vLLM #51314amd-sriramOpenopened 6 Aug

The scores buffer was created with torch.full(−inf), an FP32 fill before every logits kernel. The only reader never looks at the padding, so the fill is unnecessary. Passes clean_logits=False and uses torch.empty.

18,162 fill launches → 0; 1.25 s of GPU time removed (0.89% of kernel time). TTFT −1.1% geomean at ISL 8192, −4.9% at concurrency 32. Throughput flat, as expected for a prefill-only change.
PR #51314
7

Drop redundant −inf prefill of the decode paged MQA-logits buffer

Where: indexer stage 2, decode path. Same idea as pin 6 on the other code path.
vLLM #50008amd-sriramDraftopened 27 Jul

Removes the full-width fill_(−inf) before the decode paged logits kernel. The decode top-k bounds its scan by seq_lens and the kernels write every column it reads, so the tail is never consumed.

Saves a rows × max_model_len fp32 write per decode step. Still a draft: the FlyDSL kernel documents a −inf-prefill contract, so numeric validation across Gluon and FlyDSL paths is the exit condition. Pin B is the kernel this must agree with.
PR #50008
8

Bound the decode paged-MQA-logits sanitize to the top-k read region

Where: indexer stage 3, between scoring and top-k, decode path.
vLLM #53789amd-sriramOpenneeds-rebaseopened 25 Aug

Every decode step ran nan_to_num_(−inf) over the whole [rows, max_model_len] workspace, 43 µs per call at max_model_len 258,048 regardless of context. A small Triton kernel now sanitizes only the slice top-k reads.

Per call 43.1 µs → 4.6 µs; 426 ms → 52 ms total on rank 0. +3.2% throughput and −3.3% TPOT at concurrency 256, geomean +0.6%. gsm8k unchanged; 9 kernel tests pass.
PR #53789
9

Skip redundant sparse index remap on non-indexer layers

Where: indexer stage 5 and the IndexShare wire. The PR that directly reflects the "1 floor in 4" design.
vLLM #51309amd-sriramOpenneeds-rebasemrv1-onlyopened 6 Aug

With cross-layer index sharing, only indexer-owning layers update the shared top-k buffer, but the old path still remapped it on every layer. Now the remap runs only where a layer owns an indexer: 21 of 78 layers with index_topk_freq=4.

Remap launches −73%, remap GPU time 2,392 ms → 646 ms. Throughput +0.6% geomean, TTFT −0.9%. Bit-identical indices, so no output change.
PR #51309
10

Resolve the indexer fp8 cache dtype once at import

Where: every function in rocm_aiter_mla_sparse.py.
vLLM #53792amd-sriramOpenreadyneeds-rebaseopened 25 Aug

fp8_dtype() cannot change after import but was called on every function invocation, once per DSA layer per forward pass. Pin 3 added a module constant and wired two of six call sites; this routes all of them through it.

Code hygiene, no behavior change: six lookups per layer per pass → one at import. The only pin labelled "ready".
PR #53792

Indexer — AITER side (the kernels underneath)

A

FlyDSL gfx950 FP8 MQA logits indexer kernel

Where: indexer stage 2, the scoring kernel itself, prefill shapes. Drop-in replacement for the Triton/Gluon kernel on MI355X.
AITER #4538vpietila-amdOpen32 commitsopened 3 Aug

Two gfx950 implementations: a direct-load kernel and an LDS-staged one that uses the async global-to-LDS DMA, XOR swizzling, and 3 LDS buffers with prefetch depth 2 so only one barrier is needed. An auto-selector picks the instance per shape.

Versus Triton/Gluon on gfx950: 1.22× at 4096×4096 and 8192×8192, 3.2× at 671×131072, 10.6× at 128×32768. This is the kernel pin 6 feeds.
AITER PR #4538
B

FlyDSL paged MLA indexer

Where: indexer stage 2, the scoring kernel for decode, reading K from the paged FP8 cache through a block table (block size 64).
AITER #4221fhuizingOpen52 commitsopened 13 Jul

Computes logits[m, n] = Σ_h ReLU(⟨Q[m,h], K[n]⟩ · kv_scale[n]) · weights[m,h] on gfx950. Its distinctive feature is a ragged per-sequence next_n, so one captured graph serves any mix of 1 to num_speculative_tokens + 1 verification tokens per request, the varlen decode that MTP's confidence-scheduled verification needs.

Makes the decode indexer match what the MTP sketcher asks for: verify a different number of drafted words per request in the same step. Pins 7 and 8 operate on this kernel's output buffer.
AITER PR #4221
C

Tiered persistent radix-select decode Top-K + arch/shape dispatcher

Where: indexer stage 4, the top-k kernel that picks the 2,048 notes, called about 78 times per decode step.
AITER #4355JH-Leon-KIM-AMDOpen112 commitsopened 23 Jul

Replaces the HIP radix sort, which grows with context length (369 µs at 8K → 1,165 µs at 120K, about 15× slower than B200's persistent kernel), with a context-length-independent radix-select that is O(topK · log topK). A dispatcher inside top_k_per_row_decode routes to it only for shapes where it measurably wins.

Best cell 1.42× on gfx950 and 2.19× on gfx942 versus HIP; without the dispatcher gate it would lose on part of the grid, so the routing is as much the result as the kernel. Set-equivalent with torch.topk. Part of the GLM-5 MXFP4 MI355X perf-uplift epic.
AITER PR #4355

Mixture-of-experts room

11

Use AITER tuned GEMM for the MoE router gate

Where: the router, its gate linear layer.
vLLM #50535amd-sriramOpenneeds-rebaseopened 31 Jul

The gate's fast bf16×bf16→fp32 GEMM was gated to Hopper and Blackwell. On ROCm the input was cast to fp32 first, AITER found no tuned kernel and fell back to a plain matmul. Now the input stays bf16 and the cast moves to the small output.

Largest win among the vLLM pins: throughput +3.1%, TPOT −3.0%, TTFT −3.9% geomean over 16 sweep points, up to +4.6% at concurrency 1. 81/81 kernel tests pass on gfx950.
PR #50535
12

Match Quark exclude semantics in the shared-expert FSE check

Where: the shared expert. Decides per layer whether the shared expert may be fused into the routed experts' grouped GEMM.
vLLM #53248xuebwang-amdOpenopened 21 Aug

The check scanned the whole exclude list for the substring "shared_expert". amd/GLM-5.2-MXFP4 excludes exactly three shared-expert weights, all in the unquantized MTP layer 78, and that alone switched the fusion off for all 75 MoE layers. The fix reuses should_ignore_layer(), the same predicate Quark uses everywhere else.

Re-enables fused shared experts on layers 3–77. Pin D tunes the fused kernel this unlocks: its shapes say experts 257, top-k 9, which is 256 + the shared one.
PR #53248
D

Retune MXFP4 fused-MoE for gfx950 (TP4 + TP8)

Where: the experts' grouped GEMM kernel, MXFP4 weights, with the shared expert fused in.
AITER #4629nholmberOpenopened 7 Aug

Retunes glm5_fp4_tuned_fmoe.csv to use the mxmoe a4w4 decode kernels for the two GLM-5.2 fused-shared-expert shapes: model_dim 6144, experts 257, top-k 9, inter_dim 512 (TP4, 12 rows) and 256 (TP8, 8 rows).

End-to-end serving throughput +4.3% mean at TP4 and +3.3% at TP8 on MI355X, peak +16.5% at ISL/OSL 1024 concurrency 32. Gains concentrate at concurrency 8–64. Largest single win on the whole map.
AITER PR #4629

How the pieces fit

Read the indexer zoom top to bottom and you get the division of labour. AITER PRs A, B and C build faster kernels for scoring and top-k. vLLM PR 3 wires AITER kernels in; 4 and 5 fuse the query side and the key side of the prologue; 6, 7 and 8 stop vLLM doing wasted work around the scores; 9 makes vLLM honour IndexShare; 10 is hygiene in the same file. In the attention block, 2 fuses the RoPE, concat and cache write that run before every MLA read, and 1 keeps the MLA weights in bf16 so the model stops looping. In the MoE room, 12 unlocks the fused shared expert, D tunes the fused kernel, and 11 gives the router its fast GEMM.
